为什么以前必须要电脑

网页有一条死规矩：一个网页不能操控另一个网站的页面。抖音的关注按钮在 douyin.com 里，你的工具页在别处，中间隔着浏览器的安全沙箱，谁也碰不到谁。

所以之前的做法是：让电脑上那台已登录的浏览器去点按钮，你的手机只当遥控器。

现在的做法：让脚本直接跑在手机浏览器的抖音页面里。这样它和抖音「同源」，请求自带你的登录态，点按钮也是真人在真浏览器里点 —— 抖音风控从根上就不存在了，电脑也就不需要了。

常见问题

Q：保存书签时提示「无效网址」，存不了？
说明这个浏览器的书签只接受 http/https 开头的地址，javascript: 被当成非法网址拦掉了（华为/荣耀自带浏览器就是这样）。
这不是你操作错了，是浏览器只认 http/https 的书签地址。华为 / 荣耀自带浏览器连「编辑已有书签」也校验，所以这条路在它身上走不通。
顺带一提：如果你只是想存个普通网页链接（比如这个说明页 https://maidang0706.github.io/douyin/安装说明.html），那是正常的 https 地址，直接存就行，不会报无效。
想跑脚本，从这三条里挑一条：
① 换 Chromium 内核浏览器（Chrome / Edge / QQ浏览器等）→ 先存普通书签再编辑改代码，成功率近 100%（方式 D）；
② 装 Via 浏览器 → 原生脚本，不需要书签，一步到位（方式 B，最省事）；
③ Kiwi + 油猴（方式 C）。

Q：抓未读要多久？
约 400 个账号、每个间隔 1~2.5 秒，大约 10~15 分钟。期间把手机屏幕保持亮着、别切走这个标签页。

Q：显示失败很多？
多半是抖音风控冷却中，过 20~30 分钟再抓一次。脚本本身遇错会自动退避等待，不会硬闯。

Q：怎么取关？
取关功能已在 10-03 12:00 取消。原因：抖音对取关风控极严，手机端 iframe 一点取关就常弹「验证码中间页」，体验很差且容易失败。以后要取关，直接在抖音 App 里「关注 → 批量管理」操作最稳；脚本保留「关注新账号」的能力。

Q：数据存在哪？
存在你手机浏览器的 localStorage 里（抖音域名下）。推到 GitHub 后，原来的手机端 HTML 也能看到同一份数据。

Q：换手机/清缓存会丢吗？
会。所以抓完记得点「☁️ 推到 GitHub」；在新手机上先点「🔄 同步」或从 GitHub 拉一次即可。

直接说结论：不能后台自动跑，但「切走 = 暂停，切回来 = 继续」；就算 Via 被系统杀掉，下次打开也是从断点接着抓，不用从头再来。

切到其他 App抓取暂停（浏览器不给后台页面跑 JS），切回 Via 会自动接着抓，不用重来。
锁屏 / 息屏更狠，系统会把页面整个冻住，回来可能要重来一轮。所以脚本现在会自动申请「屏幕常亮」，抓的时候不熄屏。
Via 被系统杀后台不用重头抓：进度已写进本地，下次开抖音会提示「上次抓到 x / y，从断点继续（补剩下的）」，已抓过的不会重复请求。想「🧹 清断点」全部重抓也行。

为什么不能真后台？（这是浏览器的硬规矩，不是脚本的锅）

网页是「前台优先」的：页面看不见时浏览器就冻结它的 JS。 唯一的例外是 Service Worker 后台同步，但那需要脚本能往 douyin.com 这个域下上传文件、由你注册 PWA —— 那是抖音的域名，我们改不了。所以「挂在后台慢慢抓」这条路，在网页方案里不存在。 （当初做整套方案时的前提就是「全在真浏览器里跑」，代价就是得让页面在前台。）

⑤-3 上一版（10-02 凌晨）：失败太多 / 抓一半卡死，彻底修掉

上一版并发一开到 6，失败就变多、偶尔还整轮卡住不动。查下来是两个死穴，这次一起解决了：

① 卡死的根因：fetch 没有超时
这次是重点		抖音偶尔把连接挂着不回响应头，而老代码的 fetch 会一直「等」下去 —— 那个并发槽位就永远还不回来，整轮就停在半路、进度条也不动，看着就是「卡死」。
现在：每个请求 8 秒硬超时（到点直接掐断算失败）+ 单个账号最多卡 45 秒兜底 + 整轮 12 分钟看门狗自动收尾 + 随时可点 「🛑 停止」。任何情况下都不会停在那儿不动。
② 失败多的根因：开局就 6 个猛打一上来 6 个并发，抖音立刻限流（403 / 返回验证页）→ 失败率飙升，失败又要重试，越重试越容易被盯。
现在换成 自适应并发（悄悄提速、卡了就退）：
· 开局只打 3 个；
· 连成 5 个不失败 → 自动 +1（最多到设置的上限，默认 6）；
· 连续 2 个失败 → 并发砍半 + 冷却 2~3 秒；
· 识别出风控 → 降到 1 个 + 冷却 4~6 秒，连续 3 次直接收工（剩下的记进断点），不再硬磨。
③ 断点了：中途打断也能续上进度会写进本地。切 App、熄屏、Via 被系统杀、网络断线 —— 下次打开直接从断点接着抓，不用从头再来；断点还会自动回退到失败的那几个之前，保证一个不漏。
④ 反而更快了模拟 120 个账号：0.87 秒跑完、0 失败（并发自动升到 6）。错峰间隔 110ms→60ms、失败重试退避缩短、落盘去抖 2.5 秒、进度刷新 120ms。省掉的全是「失败重试 + 干等超时」那部分时间。
速度 / 稳定怎么选（⚙️ 设置 → 「并发上限 1~10」）：想稳就 4，想快就 8~10，默认 6 就行 —— 自适应会在 3 和上限之间自己找平衡点，不用你操心。另外还能填「整轮最长几分钟」（超时自动收尾，0 = 不限制）。
进度条现在会显示：已抓 x/y、进度条、当前并发 3/6、已用时间、预计还要多久；抖音在冷却时会明确提示「⚠ 正在降速」；结束后会列出这次没抓成的账号名。

⑤-2 还想更快？这一版又砍掉三个「隐形时间杀手」（10-02 深夜）

第一版改完后还是觉得慢，查下来真正吃时间的是排队方式和主线程被自己拖累，于是又改了四处：

① 批次 → 滑动窗口
最大提速点		原来的「一批一批」每批结束都要空等 0.3~0.8 秒，而且批尾那几个槽位是白等的（6 并发时约 1/6 的时间在空转）。
现在改成滑动窗口：谁抓完谁立刻补位，任何时候都有 N 个请求在飞，批间隔被彻底摊薄。
② 并发 3 → 6（上限 12）抖音 www.douyin.com 是 HTTP/2 —— 同域下是单连接多路复用，不受 HTTP/1.1「最多 6 个连接」的限制，所以并发可以放心开到 8~12。旧版本会自动迁移到 6。
③ 落盘去抖原来每 40 个同步写一次 localStorage（几万条视频的 JSON.stringify 会卡主线程）。现在改成去抖：停手 3 秒后只写一次，全程只写 1~2 次。
④ 进度显示节流并发后进度回调变得很密集，每次都要改 innerHTML，渲染反而抢主线程。现在150ms 更新一次，结束前强制补最后一次。

怎么调（⚙️ 设置 → 「并发上限」）

  1. 6（默认）：全部 392 个账号一轮约 2~4 分钟，实测比上一版快一倍左右。
  2. 还嫌慢 → 填 9~10；模拟测算 392 个并发 12 只要 约 10 秒纯网络等待级别。
  3. 如果进度条上「失败」数字涨得快 → 说明打太猛被风控盯上了，往回收到 3~4。
  4. 失败必然变多、一轮反而更慢的情况：账号当天已被风控冷却，这时候降并发也没用，等 20~30 分钟再抓。
这套逻辑我用 392 / 20 / 5 / 1 个账号各种组合跑过模拟：覆盖完整、不漏账号、不会提前停，并发 12 比 6 又快一倍。
提醒：提速换来的风险是更容易触发抖音风控。别打太猛 —— 保持默认 6、亮屏、别中途反复点抓取，基本不会出问题；真被风控了（大面积失败），说明该歇一会儿了。
