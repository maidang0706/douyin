为什么以前必须要电脑

网页有一条死规矩：一个网页不能操控另一个网站的页面。抖音的关注按钮在 douyin.com 里，你的工具页在别处，中间隔着浏览器的安全沙箱，谁也碰不到谁。

所以之前的做法是：让电脑上那台已登录的浏览器去点按钮，你的手机只当遥控器。

现在的做法：让脚本直接跑在手机浏览器的抖音页面里。这样它和抖音「同源」，请求自带你的登录态，点按钮也是真人在真浏览器里点 —— 抖音风控从根上就不存在了，电脑也就不需要了。

常见问题

Q：保存书签时提示「无效网址」，存不了？
说明这个浏览器的书签只接受 http/https 开头的地址，javascript: 被当成非法网址拦掉了（华为/荣耀自带浏览器就是这样）。
这不是你操作错了，是浏览器只认 http/https 的书签地址。华为 / 荣耀自带浏览器连「编辑已有书签」也校验，所以这条路在它身上走不通。
顺带一提：如果你只是想存个普通网页链接（比如这个说明页 https://maidang0706.github.io/douyin/安装说明.html），那是正常的 https 地址，直接存就行，不会报无效。
想跑脚本，从这三条里挑一条：
① 换 Chromium 内核浏览器（Chrome / Edge / QQ浏览器等）→ 先存普通书签再编辑改代码，成功率近 100%（方式 D）；
② 装 Via 浏览器 → 原生脚本，不需要书签，一步到位（方式 B，最省事）；
③ Kiwi + 油猴（方式 C）。

Q：抓未读要多久？
约 400 个账号、每个间隔 1~2.5 秒，大约 10~15 分钟。期间把手机屏幕保持亮着、别切走这个标签页。

Q：显示失败很多？
多半是抖音风控冷却中，过 20~30 分钟再抓一次。脚本本身遇错会自动退避等待，不会硬闯。

Q：取关失败 / 提示验证码？
取关是用「隐藏 iframe 打开对方主页 → 点真实关注按钮」实现的。抖音对新建的页面上下文比较敏感，你当天抓取频繁时会弹「验证码中间页」导致失败。
解决办法（任选）：
① 点账号右边的 🌐 主页，在真实标签页里手动点一下「已关注」—— 真实页面不会被验证码拦；
② 等 20~30 分钟风控冷却后再用 ✕ 取关。
这是抖音的风控策略，不是脚本坏了；同一台电脑那套也一样会被拦。

Q：数据存在哪？
存在你手机浏览器的 localStorage 里（抖音域名下）。推到 GitHub 后，原来的手机端 HTML 也能看到同一份数据。

Q：换手机/清缓存会丢吗？
会。所以抓完记得点「☁️ 推到 GitHub」；在新手机上先点「🔄 同步」或从 GitHub 拉一次即可。

数据怎么看

脚本负责「抓 + 操作」，看数据有两条路，都不需要电脑：

  1. 脚本里直接看：面板 →「📺 看未读列表」，点标题跳转、点「已读」标记
  2. 原来的手机端 HTML：抓完点「☁️ 推到 GitHub」，然后打开你手机上那个 抖音更新提醒-手机端.html 点「🔄 同步」，就能看到同一份数据（它离线时会从 GitHub 拉）
两边共用同一个 unread.json，数据格式完全一致，谁后推谁为准。

④ 抓未读的时候，能切到别的 App 吗？（10-02 再加强：现在切走也能续）

直接说结论：不能后台自动跑，但「切走 = 暂停，切回来 = 继续」；就算 Via 被系统杀掉，下次打开也是从断点接着抓，不用从头再来。

切到其他 App抓取暂停（浏览器不给后台页面跑 JS），切回 Via 会自动接着抓，不用重来。
锁屏 / 息屏更狠，系统会把页面整个冻住，回来可能要重来一轮。所以脚本现在会自动申请「屏幕常亮」，抓的时候不熄屏。
Via 被系统杀后台不用重头抓：进度已写进本地，下次开抖音会提示「上次抓到 x / y，从断点继续（补剩下的）」，已抓过的不会重复请求。想「🧹 清断点」全部重抓也行。

为什么不能真后台？（这是浏览器的硬规矩，不是脚本的锅）

网页是「前台优先」的：页面看不见时浏览器就冻结它的 JS。 唯一的例外是 Service Worker 后台同步，但那需要脚本能往 douyin.com 这个域下上传文件、由你注册 PWA —— 那是抖音的域名，我们改不了。所以「挂在后台慢慢抓」这条路，在网页方案里不存在。 （当初做整套方案时的前提就是「全在真浏览器里跑」，代价就是得让页面在前台。）

那怎么抓得省事一点？（三档，按你耐心的程度选）

  1. 最省事：亮屏、停在抖音页、别切 App，让它跑完（全部 392 个约 10~15 分钟）。现在脚本会自动申请屏幕常亮。
  2. 想中途去干别的：⚙️ 设置 → 填「每次抓前几个账号」= 80 → 保存 → 每轮约 4 分钟。 分 5 轮跑完，中间随手切 App 也不心疼（切走等于暂停）。推荐这个。
  3. 折中：抓到一半切走 → 回来 Via 会自动续上，只是进度走得慢一点。
抓的那几分钟别锁屏就好，别的都不用管。

⑤ 电脑端为什么比手机端快？这一版已经比电脑端快很多了（10-02 二次提速）

先说清楚：两边用的接口和参数是一模一样的（都是 /aweme/v1/web/aweme/post/， count=20），差别只在「怎么排队发请求」。

电脑端（CDP 驱动浏览器）一个一个串行：抓完一个，等 1~2.5 秒，再抓下一个。
手机上跑同一套逻辑就是慢的原因之一。
现在手机端并发 3 个一批一起发：浏览器内发出的同源请求抖音是放行的（有完整设备指纹 + cookie），所以手机端反而能比电脑端更快。

这一版具体改了三处（都是实打实省时间）

  1. 并发抓取：默认 3 个账号同时抓（设置里可填 1~8）。批与批之间只留 0.3~0.8 秒，不再是死等 1~2.5 秒。
    算一笔账 392 个账号：串行 ≈ 392 × 1.75 秒 ≈ 11 分钟；并发 3 ≈ 131 批 × 0.55 秒 ≈ 1.2 分钟 + 请求本身，实际一轮 4~6 分钟。
  2. 失败不再长等：以前一个账号失败就要干等 3 秒（连错 8 个还退避 30 秒）。现在失败立刻跳过、只记下来， 主流程跑完后再补抓一遍 —— 不漏数据，也不拖慢主流程。
  3. 落盘频率降档：以前每抓 10 个就往 localStorage 写一次（几千条视频的同步写入很贵，会卡一下）。 现在改成每 40 个存一次，最后一定存。

⑤-5（10-02 04:00 · v1.6）：换了个根本思路 —— 请求数从 392 次降到 3 次

上一版虽然修了 bug，但失败还是多。这次想明白了：失败多不是 bug，是「请求太多」的必然结果 —— 392 个账号就是 392 次接口请求，不管并发怎么调，抖音都会限流。所以这一版不再逐个问账号了。

① 改用「关注页信息流」
这次的关键		 抖音的「关注页」本来就把你关注的人的最新视频按时间倒序推给你，一次请求就能拿 20 条。
所以只要翻到上次抓到的时间点，就说明这个账号没有更新的了，根本不用再问它。
日常（隔几小时~一天再抓）：2~5 次请求就能核对完全部 392 个账号。仿真实测：总共 3 次请求、0 失败、1.1 秒（原来 392 次请求）。
请求少了两个数量级，抖音当然不会再限流 —— 这才是「又快又不失败」的正解。
② 参数指纹不再自相矛盾 之前请求参数里写死了「Windows / PC / 1920×1080」，可脚本实际跑在手机浏览器里 —— UA 是手机、参数却自称 PC，这种自相矛盾的指纹正是风控最爱抓的异常（电脑端串行慢抓没事，手机端一并发就大面积 403）。
现在改成照抄抖音页面自己刚刚发过的请求参数（从 performance 里读），参数永远和当前环境/抖音版本一致，还会自动剔除签名参数。
③ 未读列表不再越攒越多 信息流里翻到的旧视频不再算未读：只要不比「该账号已知的最新一条」新，就只用来判定「这个账号追平了」，不进未读列表。
④ 走不通会自动降级 万一信息流接口被抖音改掉或被风控，自动退回逐个抓（老办法照常工作），绝不会比原来更差。
设置页新增「抓取方式」：自动（推荐）/ 只逐个抓 —— 想强制用老办法可以手动切。
⑤ 进度条分两个阶段显示 进度条下的黄字会告诉你在哪一步：① 关注页信息流（一次拿 20 条，请求极少）→ ② 补抓没覆盖到的账号（首次使用会多一些，之后很少）。
关于「第一次用」：本地还没有每个账号的「最新视频时间」基线，信息流得翻得深一点，会退化为逐个补抓 —— 第一遍慢一次是正常的，从第二遍开始就是 2~5 次请求的事了。

⑤-6（10-02 12:50）：未读终于「跟抖音 App 一模一样」了 —— 看了就会少

你测出来的问题很准：看了几个未读视频，未读数量却一点没变。原因不是抓取失败，是「未读」这个定义从一开始就是假的 —— 以前的算法是「抓到的视频 − 本机点过的已读」，可你在抖音 App 里看过的视频，我们这边根本不知道 → 一堆早就看过的旧视频一直挂在未读里，真正的新未读被淹没，数字看着就一动不动。

① 改读抖音自己的「已看记录」
这次的关键		 抖音服务器本身记着你看过哪些视频（观看历史，App / 网页端都写进去、跨设备同步），接口是 /aweme/v1/web/history/read/。
现在每轮抓取先花 1~2 次请求把它读一遍，然后：
未读 = 抓到的新视频 − 抖音已看记录 − 本机标记已读。
于是：你在抖音里看完 → 下一轮抓取它自动从列表消失，和 App 的红点一模一样。只多 1~2 次请求，不影响速度。
② 旧账一次清干净 以前攒下的、你其实早看过的旧视频，第一次抓取就会一次性从未读里划掉并写进已读记录（推到 GitHub 后，手机端 HTML 那边也不会再算未读）。
③ 在本面板里看完自动标已读 点未读列表里的标题会用抖音打开，打开看完就自动记已看，不用再去点那颗「已读」（「已读」按钮保留，当手动撤销用）。

④ 结果页会说实话 抓完显示：新增未读 N 条 / 抖音里看过的 N 条（已剔除）/ 当前未读合计 N 条。
万一「已看记录」接口读不到（403 之类），进度条会黄字提示，抓取照常，不会崩。
⑤ 版本号换了个写法 面板标题后面的小灰字不再写 v1.6，改成 生成日期时间（10-02 12:50），完整改动说明放在鼠标悬停和设置页最下面 —— 一眼就知道手机上跑的是哪天那版。

⑤-5（10-02 04:00 · v1.6）：换了个根本思路 —— 请求数从 392 次降到 3 次

你反馈「失败太多、经常卡住」—— 这次挖到了一个藏得很深的代码 bug，修完之后失败率基本归零，顺带把进度显示换成了真正的进度条。

① 真凶：并发窗口的游标没往前走
这次的关键		 排队函数里取账号时漏了一句「游标 +1」，结果是：所有并发通道都在反复请求同一个账号。
3~6 个请求同一毫秒打向同一个账号 → 抖音立刻判定异常限流 → 大面积 403 / 验证页 = 你看到的「失败太多」；同时后面的账号根本没被派发，进度看着就「卡住」了。
已修：每个通道取走一个账号后游标立刻前进，一个账号一次只被一个请求碰。
② 抖一下不算失败：就地重试 3 次 以前一次超时/一个 403 就直接记「失败」。现在单个账号失败会立刻退避重试（共 3 次机会），风控类错误等 2.5~5 秒再来；整轮跑完还会把剩下的再补 最多 2 轮。
界面上会显示「自动重试 N 次」，这些全部算成功，不进失败数。
③ 不会再误判风控而半途放弃 以前「连续 3 个账号失败」就整轮收工，结果刚打开页面时的短暂限流会被误当成全局风控，几百个账号白等一轮。
现在改成看成功率：至少试过 12 个账号、成功率还不到 25%，才认定抖音在全局限流并收尾（剩下的进断点下次补）。开头偶尔挂几个 → 照常继续抓。
④ 再加一道「不卡死」保险 原有：每请求 8 秒超时 / 单账号 45 秒 / 整轮 12 分钟看门狗。新增：90 秒没有任何进展 → 强制收尾（未完成的进断点）。四层保险叠加，不存在停住不动的情况。
⑤ 真进度条（你要的完成率） 不再是字符方块，换成大号完成率百分比 + 带流动条纹的进度条：
· 顶部 37% 大数字 + 148 / 392；
· 进度条平滑推进，颜色会变：红=正常 / 橙=降速冷却 / 深红=限流重试 / 绿=完成；
· 下面实时显示 成功 / 失败 / 新增 / 并发 / 已用 / 预计还需 / 自动重试次数 / 当前账号；
· 结束后结果显示 完成率 xx%。
仿真实测（26 项断言全过）：
· 120 个账号全正常 → 0 失败，每个账号恰好请求 1 次（修复前是同一个账号被请求几十次）；
· 80 个账号、20% 随机抖动 → 靠就地重试最终 0 失败；
· 40 个账号、15% 请求永久挂起（最恶劣）→ 0 失败、不卡死；
· 开头 8 个死活失败 + 后面正常 → 不误判收工，后面 32 个全部抓到，失败数准确显示 8。
关于速度：修好这个 bug 后，同一时间发出的请求才是真正分摊到不同账号，等于白捡数倍吞吐；再加上「连成 6 个就加一档并发」的提速，正常情况下比上一版明显更快，而且因为不再触发限流，反而省掉了大量失败重试的时间。

⑤-3 上一版（10-02 凌晨）：失败太多 / 抓一半卡死，彻底修掉

上一版并发一开到 6，失败就变多、偶尔还整轮卡住不动。查下来是两个死穴，这次一起解决了：

① 卡死的根因：fetch 没有超时
这次是重点		抖音偶尔把连接挂着不回响应头，而老代码的 fetch 会一直「等」下去 —— 那个并发槽位就永远还不回来，整轮就停在半路、进度条也不动，看着就是「卡死」。
现在：每个请求 8 秒硬超时（到点直接掐断算失败）+ 单个账号最多卡 45 秒兜底 + 整轮 12 分钟看门狗自动收尾 + 随时可点 「🛑 停止」。任何情况下都不会停在那儿不动。
② 失败多的根因：开局就 6 个猛打一上来 6 个并发，抖音立刻限流（403 / 返回验证页）→ 失败率飙升，失败又要重试，越重试越容易被盯。
现在换成 自适应并发（悄悄提速、卡了就退）：
· 开局只打 3 个；
· 连成 5 个不失败 → 自动 +1（最多到设置的上限，默认 6）；
· 连续 2 个失败 → 并发砍半 + 冷却 2~3 秒；
· 识别出风控 → 降到 1 个 + 冷却 4~6 秒，连续 3 次直接收工（剩下的记进断点），不再硬磨。
③ 断点了：中途打断也能续上进度会写进本地。切 App、熄屏、Via 被系统杀、网络断线 —— 下次打开直接从断点接着抓，不用从头再来；断点还会自动回退到失败的那几个之前，保证一个不漏。
④ 反而更快了模拟 120 个账号：0.87 秒跑完、0 失败（并发自动升到 6）。错峰间隔 110ms→60ms、失败重试退避缩短、落盘去抖 2.5 秒、进度刷新 120ms。省掉的全是「失败重试 + 干等超时」那部分时间。
速度 / 稳定怎么选（⚙️ 设置 → 「并发上限 1~10」）：想稳就 4，想快就 8~10，默认 6 就行 —— 自适应会在 3 和上限之间自己找平衡点，不用你操心。另外还能填「整轮最长几分钟」（超时自动收尾，0 = 不限制）。
进度条现在会显示：已抓 x/y、进度条、当前并发 3/6、已用时间、预计还要多久；抖音在冷却时会明确提示「⚠ 正在降速」；结束后会列出这次没抓成的账号名。

⑤-2 还想更快？这一版又砍掉三个「隐形时间杀手」（10-02 深夜）

第一版改完后还是觉得慢，查下来真正吃时间的是排队方式和主线程被自己拖累，于是又改了四处：

① 批次 → 滑动窗口
最大提速点		原来的「一批一批」每批结束都要空等 0.3~0.8 秒，而且批尾那几个槽位是白等的（6 并发时约 1/6 的时间在空转）。
现在改成滑动窗口：谁抓完谁立刻补位，任何时候都有 N 个请求在飞，批间隔被彻底摊薄。
② 并发 3 → 6（上限 12）抖音 www.douyin.com 是 HTTP/2 —— 同域下是单连接多路复用，不受 HTTP/1.1「最多 6 个连接」的限制，所以并发可以放心开到 8~12。旧版本会自动迁移到 6。
③ 落盘去抖原来每 40 个同步写一次 localStorage（几万条视频的 JSON.stringify 会卡主线程）。现在改成去抖：停手 3 秒后只写一次，全程只写 1~2 次。
④ 进度显示节流并发后进度回调变得很密集，每次都要改 innerHTML，渲染反而抢主线程。现在150ms 更新一次，结束前强制补最后一次。

怎么调（⚙️ 设置 → 「并发上限」）

  1. 6（默认）：全部 392 个账号一轮约 2~4 分钟，实测比上一版快一倍左右。
  2. 还嫌慢 → 填 9~10；模拟测算 392 个并发 12 只要 约 10 秒纯网络等待级别。
  3. 如果进度条上「失败」数字涨得快 → 说明打太猛被风控盯上了，往回收到 3~4。
  4. 失败必然变多、一轮反而更慢的情况：账号当天已被风控冷却，这时候降并发也没用，等 20~30 分钟再抓。
这套逻辑我用 392 / 20 / 5 / 1 个账号各种组合跑过模拟：覆盖完整、不漏账号、不会提前停，并发 12 比 6 又快一倍。
提醒：提速换来的风险是更容易触发抖音风控。别打太猛 —— 保持默认 6、亮屏、别中途反复点抓取，基本不会出问题；真被风控了（大面积失败），说明该歇一会儿了。
